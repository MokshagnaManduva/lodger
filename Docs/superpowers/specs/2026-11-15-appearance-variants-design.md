# Appearance variants — design

Date: 2026-11-15. Sub-project 3 of 3. The owner chose "palette swaps plus prop
options". This spec records the design choices made without a further review round.

## Approach

A pack declares **appearance choices**; each option is a **colour map** the engine
applies once, when it loads an atlas. Considered and rejected: shipping a separate
atlas per look. Two independent choices would need every combination as a file
(Norn: 7 atlases × each combination), and each would need its own validated mask.
A colour map is a few bytes, composes across choices, and cannot change alpha, so
the existing hit masks, anchors and timings stay valid by construction.

```json
"appearance": [
  { "id": "emblem", "label": "Sun emblem", "default": "gold", "options": [
      { "id": "gold",   "label": "Gold" },
      { "id": "silver", "label": "Silver",
        "recolor": { "#fad367": "#d9dde2", "#dba639": "#a7adb5" } } ] }
]
```

- An array, so Settings shows choices and options in the author's order.
- `recolor` maps exact opaque `#rrggbb` source colours to replacements. Alpha is
  never touched. An option without `recolor` is the art as drawn.
- Format 2 only. Limits: 8 choices, 16 options each, 64 colours per option.
- Validation (engine loader and `packtool validate`): ids unique; `default` names
  an option; colours are `#rrggbb`; no source colour appears under two different
  choices (the result would depend on order).
- Still inert data: a lookup table, no expressions. Applied once per atlas load,
  never per frame; nothing is scheduled (Rule 2). Pixel art atlases have binary
  alpha, so exact colour matching is well defined.

## Limits of this approach, stated plainly

- It recolours; it cannot add, remove or reshape a prop. "No emblem" for Klien is
  therefore not offered: it would need different pixels under the emblem, a new
  mask, and a toss animation with nothing in the hand. A future `textures`
  override per option could add that.
- A colour shared by two parts of a drawing changes in both. Klien's hat, hair,
  suit and cape share one dark ramp, so his colourways tint all four together.
  They are offered as whole-figure "colourways", not as "suit colour". Separating
  hair would mean re-authoring the base art with a distinct hair ramp, which is an
  art decision for the owner.
- Norn's props are baked into generated sheets. Her flask's purples are a distinct
  hue family, so potion colour works cleanly; her irises share two of those
  purples and shift slightly with it.

## The reference packs

- **Klien** (generated by `animate_klien.py`): Colourway — Classic, Midnight,
  Burgundy, Forest; Sun emblem — Gold, Silver, Rose gold.
- **Norn** (`pack.source.json`, maps written by `build_norn.py`): Potion — Violet,
  Emerald, Amber, Azure.

These are new looks for owner art approval; the default of every choice is the
existing art, byte for byte.

## Engine and app

- `Pack.appearance`, `Pack.recolorTable(selection:)`, and `Recolor.apply(_:table:)`
  (decode to RGBA8, remap opaque pixels, re-encode). `Pet(loaded:scale:appearance:)`
  applies the table in its atlas loader.
- `Preferences` stores the selection per pack; unknown saved ids fall back to the
  default. `AppController.setAppearance` saves and, for the running character,
  recreates it in place (as resize does). Reset Character Settings clears it.
- Settings gains an **Appearance** tab: one pop-up per choice, a live preview of
  the pack's preview image with the selection applied, and Reset Appearance. The
  Character tab preview uses the same recoloured image.

## Testing

Engine: decoding, table composition, every validation rejection, pixel-exact
recolour with alpha preserved, empty selection returns the original image.
Packs: every `recolor` source colour exists in that pack's atlases; defaults are
the unmodified art. App: persistence, fallback for unknown ids, recreation in
place, reset, tab contents. Renders of each look are written to `build/` for
inspection. Not covered: owner approval of the looks, live desktop acceptance.
